This is the *inbound* counterpart to the outbound [calendar feed](calendar-feed.md) (which exports now's own todos as ICS for external calendar apps to subscribe to). Here, an external ICS feed (e.g. a Google Calendar) is imported *into* now as a `calendar` item and its child `calendar_event` items ([item types](item-types.md)).

**Registry flags.** `calendar` has `allowsUserChildren: false` (only a sync may create children under it — a person can't add or drag an item in) and `editable: true` (the item itself, and its `calendar_url`, are hand-edited normally — `PATCH /todos/{id}` stores `calendar_url` when present in the body, and an explicit `null` clears it). `calendar_event` has `allowsUserChildren: false` and `editable: false` (a synced event can't be hand-edited, retyped, moved or deleted — it's expected to be overwritten or removed by the next sync). Both flags, and their enforcement points (server 400s on split/reparent, client menu/drag gating), are generic registry mechanics documented in [item types](item-types.md), not special-cased here. `calendar_event` also carries `notifies: true` and `appearsInNextUp: true` (like `todo`), so a synced event with a due date shows up in Next up, the push digest/heads-up and the outbound [calendar feed](calendar-feed.md) alongside hand-made todos — see [item types](item-types.md) for that cross-feature note.

**Parsing/diffing (pure, no I/O).** `app/calendar_sync.py`: `parse_ics(raw, window_start, window_end, tz: ZoneInfo | None = None)` expands recurrence (`icalendar` + `recurring_ical_events`) into `ParsedEvent`s for every occurrence starting in `[window_start, window_end)`, window is `[today, today + 60 days)` (`WINDOW_DAYS`). A recurring VEVENT's `external_uid` folds in its own occurrence start time (`base_uid:iso_start`) so it stays stable across syncs even as the window slides (a bare UID would flip between "one occurrence in window" and "two" as a bounded series' tail passes out of view, breaking the create/update match on the next sync); a non-recurring event keeps its bare UID. All-day events land at midnight ([due time](due-time.md) convention). `due_date` is a floating wall-clock time everywhere in this app, never a UTC instant (same reasoning as the outbound feed's floating-time export in `app/ics.py`) — so a timezone-aware DTSTART (`TZID=...` or a `Z`-suffixed UTC time) is converted to `tz`'s wall-clock time (`start.astimezone(tz).replace(tzinfo=None)`), not UTC's; `tz` defaults to `ZoneInfo("UTC")` when omitted, so floating-time fixtures/callers (no `tzinfo` at all) are unaffected either way. `run_calendar_sync` passes the *home* timezone (the most-recently-seen device's, via `tasks.home_tz(db.list_push_devices())` + `push._zone(...)`, falling back to UTC with no devices) so a real-world tz-aware feed event lands at the same wall-clock hour a device would show it at. `diff_events(desired, existing)` matches by `external_uid` against the calendar's current `calendar_event` children and returns `(to_create, to_update, to_delete_ids)` — `to_update` only includes an event whose title/due_date/location actually changed, so an unchanged occurrence gets no write at all.

**Writing.** `db.apply_calendar_sync(calendar_id, events, triggered_by=None)` (`app/db_firestore.py`) runs the whole diff in one `run_atomic` transaction (passing `triggered_by` through to it — see [sync model](sync-model.md)): a changed-but-still-present event is patched in place (same `todo_id`, `version` bumped once), never deleted+recreated — `remote-diff.js` identifies items by `todo_id`, so a delete+recreate would make every routine resync of an unchanged calendar look like a spurious "N changes from another device" on other clients. New children get `order_idx` assigned up front (like `split_into_children`), not read lazily per-create, because Firestore forbids a read after a write inside one transaction and a sync can create several events in the same call. `db.mark_calendar_synced(calendar_id, error)` records `last_synced_at`/`last_sync_error` as a server-managed field (no `If-Match`/version bump, like `collapsed` — must never conflict with a concurrent user edit).

**Fetching.** `calendar_sync.run_calendar_sync(calendar_id, fetch=None, client_session_id=None)` (`fetch` defaults to `_http_fetch`, a 10s-timeout `requests.get`) ties it together: no-ops with `{"synced": False, "reason": "no calendar_url"}` if the calendar has none; on any exception (fetch or parse) it records `last_sync_error` and returns `{"synced": False, "error": ...}` **without touching existing events** — a dead/slow feed degrades to "stale" rather than wiping the calendar's children. It never raises (mirrors `push.py`'s internal-job convention): a Cloud Task delivery always acks, never retries into a storm. `client_session_id` (when given) is threaded straight into `apply_calendar_sync`'s `triggered_by`.

**Triggers — one shared staleness check.** `tasks.enqueue_calendar_sync(calendar_id, last_synced_at, now_utc, threshold=CALENDAR_STALE_AFTER, client_session_id=None)` (`CALENDAR_STALE_AFTER = 6h`) is the single staleness predicate every caller shares. `last_synced_at` comes back from Firestore without tzinfo (`mark_calendar_synced` stores naive UTC), so the predicate treats a naive value as UTC before comparing it with the aware `now_utc`; the whole check is inside its `try`, so it never raises into the tree/root nudge or the daily digest:
- `GET /todos/tree` and `GET /todos/root` ([routes](../api/routes.md)) each nudge every live `calendar` in the just-loaded list, via `BackgroundTasks` (`app/routes/todos.py`'s `_nudge_stale_calendars`) — runs after the response is sent, so a slow feed adds no read latency (`enqueue_calendar_sync` itself is a fast Cloud Tasks API call, not the ICS fetch). No `client_session_id`: nothing to attribute a load-triggered nudge to. `GET /todos/next` is deliberately excluded: `calendar`s never `appearsInNextUp`, so nudging there would be redundant with the tree/root nudges.
- `POST /todos/{id}/sync` ("Sync now") calls it with `last_synced_at=None`, forcing the staleness check to always trigger, and threads the request body's `client_session_id` through to `enqueue_calendar_sync` → the Cloud Task body → `run_calendar_sync` → `apply_calendar_sync`'s `triggered_by`, so the rev bump this sync eventually causes carries the calling client's session id ([sync model](sync-model.md)). The client exposes this as a **Sync now** button in a `calendar` item's own viewer (`web/editors.js`'s `renderViewer`, `web/app.js`'s `syncCalendarNow`), alongside last-synced/error status read straight off the todo (`last_synced_at`/`last_sync_error`, both already on the tree/root payload) — no extra request. The button only fires the async server-side sync; it doesn't wait for or reflect completion, since the client has no push channel for that (a later tree/root load, or the next visit, picks up the refreshed `calendar_event` children and status once the Cloud Task finishes). The `client_session_id` sent here is also how the *triggering* window recognizes the resulting rev bump as its own and suppresses the "changes from another device" mascot line for it — see [sync model](sync-model.md)'s provenance section.
- The daily digest (`app/push.py`'s `run_notify`) also nudges every `calendar` in the tree once a day, so a calendar with no client ever open still refreshes. No `client_session_id` either.

`tasks.create_calendar_sync_task(calendar_id, client_session_id=None, now_utc=None)` enqueues a Cloud Task at `/internal/sync-calendar/{calendar_id}` (reuses the reminder queue/OIDC plumbing), bucketed by hour so repeat page loads in the same hour dedupe to one task; a manual **Sync now** (`manual=True`, passed via `enqueue_calendar_sync(..., manual=True)`) is instead named per minute with a `-manual` suffix, so it isn't swallowed by an earlier page-load task in the same hour; `client_session_id` rides along in the task body. `POST /internal/sync-calendar/{id}` (`app/routes/notifications.py`, Cloud Tasks OIDC auth only) calls `run_calendar_sync` with the body's `client_session_id`.

**Tests.** `tests/test_calendar_sync.py` covers parsing/diffing, `apply_calendar_sync`/`mark_calendar_synced`, `run_calendar_sync` (success, no-URL no-op, fetch-failure-keeps-existing-events, via a dependency-injected `fetch`), the `POST /todos/{id}/sync` route (202/400, and that it threads `client_session_id`) and the tree-read nudge. Manually verified `_http_fetch` against a real Google Calendar ICS URL: valid ICS, 115 events parsed in the 60-day window.
