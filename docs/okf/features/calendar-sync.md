This is the *inbound* counterpart to the outbound [calendar feed](calendar-feed.md) (which exports now's own todos as ICS for external calendar apps to subscribe to). Here, an external ICS feed (e.g. a Google Calendar) is imported *into* now as a `calendar` item and its child `calendar_event` items ([item types](item-types.md)).

**Registry flags.** `calendar` has `allowsUserChildren: false` (only a sync may create children under it — a person can't add or drag an item in) and `editable: true` (the item itself, and its `calendar_url`, are hand-edited normally — `PATCH /todos/{id}` stores `calendar_url` when present in the body, and an explicit `null` clears it; the client only sends fields listed in `web/sync.js`'s `PATCH_FIELDS`, which must match `TodoUpdate` — `tests/test_patch_fields_parity.py` enforces it). `calendar_event` has `allowsUserChildren: false` and `editable: false` (a synced event can't be hand-edited, retyped, moved or deleted — it's expected to be overwritten or removed by the next sync). Both flags, and their enforcement points (server 400s on split/reparent, client menu/drag gating), are generic registry mechanics documented in [item types](item-types.md), not special-cased here. `calendar_event` also carries `notifies: true` and `appearsInNextUp: true` (like `todo`), so a synced event with a due date shows up in Next up, the push digest/heads-up and the outbound [calendar feed](calendar-feed.md) alongside hand-made todos — see [item types](item-types.md) for that cross-feature note.

**Parsing/diffing (pure, no I/O).** `app/calendar_sync.py`: `parse_ics(raw, window_start, window_end, tz=None, *, now=None, series_window_end=None)` expands recurrence (`icalendar` + `recurring_ical_events`) and returns `ParsedEvent`s:
- **One-off events:** every one starting in `[window_start, window_end)`, keyed by their bare UID. `run_calendar_sync` uses `[today, today + 60 days)` (`WINDOW_DAYS`).
- **Recurring series (RRULE/RDATE): only the next occurrence** (user decision 2026-09-22: a daily standup must not become 60 rows). That is the earliest occurrence in `[window_start, series_window_end)` that has not *ended* by `now` (a meeting in progress stays; an all-day occurrence with no end lasts its whole day). `run_calendar_sync` looks 366 days ahead (`SERIES_WINDOW_DAYS`) so a yearly event months away still shows. The series is keyed by its **bare UID**, so the same item is patched in place as the series moves forward or the organizer moves an instance. EXDATEs and moved instances (RECURRENCE-ID overrides) are honoured by the expander. Whether a UID is a series is read from the source VEVENT, not from the window (`recurring_ical_events` 2.2.3 doesn't set RECURRENCE-ID on expanded occurrences). Before this change every occurrence was its own item keyed `uid:start`, so a time change deleted and recreated items; the first sync after deploy replaces those per-occurrence items with one per series.
- **Cancelled** events (`STATUS:CANCELLED`, whole event or one instance) are left out.
- **Copied fields** (all on `calendar_event`, [Todo](../data/todo.md); `ParsedEvent.todo_fields()` is the one list that is both written and compared): `title` (SUMMARY), `due_date` (DTSTART), `end_date` (DTEND, or DTSTART + DURATION; all-day = exclusive next midnight; `None` if absent), `location` (LOCATION only; the old fallback to DESCRIPTION is gone), `notes` (DESCRIPTION as plain text: Google's HTML is flattened and its `-::~:~::-` dial-in block removed; capped at `MAX_NOTES_LEN`), `repeat_summary` (the series' RRULE in words via `describe_rrule`, e.g. "Every weekday", "Weekly on Mon, Wed", "Monthly on the 2nd Tue"; `None` for a one-off), `conference_url` (`X-GOOGLE-CONFERENCE`, else RFC 7986 `CONFERENCE`, else the first Meet/Zoom/Teams/Webex URL in the location or description) and `attendees` (each ATTENDEE as `{name, email, status, organizer}`, status one of accepted/declined/tentative/needs-action, anything else counts as needs-action; a CN that only repeats the email is dropped; rooms/resources (`CUTYPE=RESOURCE|ROOM`, `@resource.calendar.google.com`) are left out; capped at `MAX_ATTENDEES`). Attendees are only there when the feed includes them: Google's secret iCal address does for events whose guest list you can see; Outlook published calendars often strip them. This stores other people's names and emails, which the user chose explicitly (2026-09-22).
- **Not copied (yet):** your own RSVP as a filter (would need your email per calendar), TRANSP, VALARM, ORGANIZER beyond the attendee flag, CATEGORIES/CLASS/PRIORITY/ATTACH/GEO.

All-day events land at midnight ([due time](due-time.md) convention). `due_date`/`end_date` are floating wall-clock times everywhere in this app, never UTC instants (same reasoning as the outbound feed's floating-time export in `app/ics.py`), so a timezone-aware DTSTART/DTEND (`TZID=...` or `Z`) is converted to `tz`'s wall-clock time; `tz` defaults to UTC, and floating times are never converted. `run_calendar_sync` passes the *home* timezone (the most-recently-seen device's, via `tasks.home_tz(db.list_push_devices())` + `push._zone(...)`, UTC with no devices), and computes `now`/`today` on that same wall clock (it used the UTC date until 2026-09-22, which started the window a day early every evening west of Greenwich and dropped that evening's events). `diff_events(desired, existing)` matches by `external_uid` against the calendar's current `calendar_event` children and returns `(to_create, to_update, to_delete_ids)`; `to_update` only includes an event where some copied field actually changed, so an unchanged event gets no write at all.

**In the UI.** A `calendar_event` row shows the repeat chip with `repeat_summary` (same chip as a todo's repeat rule, `renderMeta` in `web/ui-helpers.js`). Its viewer (`renderViewer`, `web/editors.js`) shows **When** (`Due.formatSpan`: "Thursday 2:00 PM – 3:30 PM", all-day spans as "Friday – Sunday"), **Repeats**, **Location**, **Video call** (a "Join call" link, only for a safe http(s) URL), **Guests** (summary "2 going · 1 maybe · 1 no reply · 1 not going", then each guest: organizer first, then going, maybe, no reply, not going; name or email; declined names dimmed; `Fields.sortedGuests`/`guestSummary`/`guestStatusLabel` in `web/fields.js`) and **Notes**. The new fields are in `calendar_event`'s registry `fields` and in `ItemForm.FIELD_GROUPS` (no input: sync-only, like `location`). The outbound [calendar feed](calendar-feed.md) uses `end_date` when present.

**Writing.** `db.apply_calendar_sync(calendar_id, events, triggered_by=None)` (`app/db_firestore.py`) runs the whole diff (creates, in-place updates, hard deletes) in one `run_atomic` transaction (passing `triggered_by` through to it — see [sync model](sync-model.md)): a changed-but-still-present event (including a series stepping to its next occurrence) is patched in place, every copied field set from `ParsedEvent.todo_fields()` (same `todo_id`, `version` bumped once), never deleted+recreated — `remote-diff.js` identifies items by `todo_id`, so a delete+recreate would make every routine resync of an unchanged calendar look like a spurious "N changes from another device" on other clients. New children get `order_idx` assigned up front (like `split_into_children`), not read lazily per-create, because Firestore forbids a read after a write inside one transaction and a sync can create several events in the same call. `db.mark_calendar_synced(calendar_id, error)` records `last_synced_at`/`last_sync_error` as a server-managed field (no `If-Match`/version bump, like `collapsed` — must never conflict with a concurrent user edit).

**Removal is a hard delete (2026-09-22, user decision).** A synced event holds nothing the user wrote and the feed is the source of truth, so events never go to the trash:
- **Gone from the feed:** `apply_calendar_sync` deletes the document outright (`_delete`, inside the same transaction; the rev bump tells other clients). It used to soft-delete, which filled the Trash with every past event and the one-off migration to one-item-per-series.
- **Deleting the calendar** (or anything containing one, e.g. a list): the calendar itself is soft-deleted as usual (Trash, Undelete, 30-day archive), but its events are hard-deleted in the same transaction. `db.calendar_purge_plan(todo)` does the reads (the calendar itself, or every `type == "calendar"` document that `todo` is an ancestor of, plus their `calendar_event` children) before any write; `db.apply_calendar_purge(plan, todo)` deletes the events and clears each calendar's `last_synced_at`. Both `DELETE /todos/{id}` and `PATCH` with `deleted: true` use them. Undeleting brings the calendar back empty; with `last_synced_at` cleared, the next tree load's staleness check syncs it again. The client mirrors this: `web/sync.js`'s `delete` op leaves `calendar_event` nodes out of its undo snapshot and empties the calendar's `child_ids`, so Undo doesn't show stale events.
- **Backstop:** `db.purge_stale_calendar_events()` runs in the daily housekeeping (`maybe_archive_expired`, before `archive_expired`) and hard-deletes any `calendar_event` nobody can see: flagged deleted, under a calendar that is missing, deleted or inside something deleted, or in the archive. This cleaned up the events earlier syncs had soft-deleted, and covers paths that trash a calendar without a purge (Clear completed). Plain writes, no rev bump (none of these is in the live tree).

**Fetching.** `calendar_sync.run_calendar_sync(calendar_id, fetch=None, client_session_id=None)` (`fetch` defaults to `_http_fetch`, a 10s-timeout `requests.get`) ties it together: no-ops with `{"synced": False, "reason": "no calendar_url"}` if the calendar has none; on any exception (fetch or parse) it records `last_sync_error` and returns `{"synced": False, "error": ...}` **without touching existing events** — a dead/slow feed degrades to "stale" rather than wiping the calendar's children. It never raises (mirrors `push.py`'s internal-job convention): a Cloud Task delivery always acks, never retries into a storm. `client_session_id` (when given) is threaded straight into `apply_calendar_sync`'s `triggered_by`.

**Triggers — one shared staleness check.** `tasks.enqueue_calendar_sync(calendar_id, last_synced_at, now_utc, threshold=CALENDAR_STALE_AFTER, client_session_id=None)` (`CALENDAR_STALE_AFTER = 6h`) is the single staleness predicate every caller shares. `last_synced_at` comes back from Firestore without tzinfo (`mark_calendar_synced` stores naive UTC), so the predicate treats a naive value as UTC before comparing it with the aware `now_utc`; the whole check is inside its `try`, so it never raises into the tree/root nudge or the daily digest:
- `GET /todos/tree` and `GET /todos/root` ([routes](../api/routes.md)) each nudge every live `calendar` in the just-loaded list, via `BackgroundTasks` (`app/routes/todos.py`'s `_nudge_stale_calendars`) — runs after the response is sent, so a slow feed adds no read latency (`enqueue_calendar_sync` itself is a fast Cloud Tasks API call, not the ICS fetch). No `client_session_id`: nothing to attribute a load-triggered nudge to. `GET /todos/next` is deliberately excluded: `calendar`s never `appearsInNextUp`, so nudging there would be redundant with the tree/root nudges.
- `POST /todos/{id}/sync` ("Sync now") calls it with `last_synced_at=None`, forcing the staleness check to always trigger, and threads the request body's `client_session_id` through to `enqueue_calendar_sync` → the Cloud Task body → `run_calendar_sync` → `apply_calendar_sync`'s `triggered_by`, so the rev bump this sync eventually causes carries the calling client's session id ([sync model](sync-model.md)). The client exposes this as a **Sync now** button in a `calendar` item's own viewer (`web/editors.js`'s `renderViewer`, `web/app.js`'s `syncCalendarNow`), alongside last-synced/error status read straight off the todo (`last_synced_at`/`last_sync_error`, both already on the tree/root payload) — no extra request. The button only fires the async server-side sync; it doesn't wait for or reflect completion, since the client has no push channel for that (a later tree/root load, or the next visit, picks up the refreshed `calendar_event` children and status once the Cloud Task finishes). The `client_session_id` sent here is also how the *triggering* window recognizes the resulting rev bump as its own and suppresses the "changes from another device" mascot line for it — see [sync model](sync-model.md)'s provenance section.
- The daily digest (`app/push.py`'s `run_notify`) also nudges every `calendar` in the tree once a day, so a calendar with no client ever open still refreshes. No `client_session_id` either.

`tasks.create_calendar_sync_task(calendar_id, client_session_id=None, now_utc=None)` enqueues a Cloud Task at `/internal/sync-calendar/{calendar_id}` (reuses the reminder queue/OIDC plumbing), bucketed by hour so repeat page loads in the same hour dedupe to one task; a manual **Sync now** (`manual=True`, passed via `enqueue_calendar_sync(..., manual=True)`) is instead named per minute with a `-manual` suffix, so it isn't swallowed by an earlier page-load task in the same hour; `client_session_id` rides along in the task body. `POST /internal/sync-calendar/{id}` (`app/routes/notifications.py`, Cloud Tasks OIDC auth only) calls `run_calendar_sync` with the body's `client_session_id`.

**Tests.** `tests/test_calendar_sync.py` covers parsing/diffing (next-occurrence-only series, stepping forward once an occurrence ends, EXDATE and moved instances, the long series window, all-day series, details/attendees/cancelled via `fixtures/calendar/details.ics` and `series.ics`, `describe_rrule`), storing and updating the new fields in place, hard deletes (sync removal, deleting a calendar or a list holding one, PATCH `deleted`, undelete restoring the calendar empty, the stale-event sweep incl. the archive), the home-timezone window date, `apply_calendar_sync`/`mark_calendar_synced`, `run_calendar_sync` (success, no-URL no-op, fetch-failure-keeps-existing-events, via a dependency-injected `fetch`), the `POST /todos/{id}/sync` route (202/400, and that it threads `client_session_id`) and the tree-read nudge. Manually verified `_http_fetch` against a real Google Calendar ICS URL: valid ICS, 115 events parsed in the 60-day window.
